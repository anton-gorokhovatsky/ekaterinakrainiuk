# Проверка UX перед сдачей

Применяется вместе с обязательными [правилами UX](ux-rules.md), [дизайн-направлением](design-direction.md) и `AGENTS.md`. Основания рекомендаций — в [каталоге NN/g и W3C](nng-sources.md). Чеклист помогает принять конкретную правку; он не означает, что весь сайт уже прошёл аудит.

## До изменения

- [ ] Сформулировать задачу посетителя, дефект и ожидаемый результат. Для изменения структуры отделить гипотезу от наблюдения за людьми.
- [ ] Определить область работы: один элемент, компонент с состояниями, общий токен или несколько разделов. Свериться с принятыми решениями и источниками содержания.
- [ ] Выбрать относящиеся к задаче правила UX-01–UX-32 и необходимые способы проверки. Не запускать полный исследовательский проект ради исправления одного угла.
- [ ] Перед крупным экспериментом проверить точку восстановления; сохранить незавершённую работу и не перемещать существующие восстановительные теги.

## Во время правки

- [ ] Смысл и порядок: до действия видно достаточно для выбора; подпись обещает фактический следующий шаг; цена и существенные условия не скрыты.
- [ ] Композиция: общие оси сохранены; родственные элементы сближены; заголовки, интервалы и акценты выражают правильную иерархию. Посмотреть соседние блоки, а не только обрезанный фрагмент.
- [ ] Управление: вся предусмотренная область принимает действие; нет обязательного лишнего раскрытия; доступность действия понятна до hover. Фокус, наведение, выбор и открытие различаются.
- [ ] Содержание: факты, цены и цитаты подтверждены; фотографии не подменены; висячая пунктуация, переносы и кадрирование сохранены.
- [ ] Общая система: использованы существующие роли и токены; новая частная поправка не расходится с родственными компонентами.

## Выбор глубины проверки

Для изменения интерфейса базовый визуальный контроль — изменённая область с соседями, обе темы, широкий и узкий экран. Дополнительные состояния выбираются по риску. «Не применимо» означает конкретную причину, а не отсутствие времени.

| Что меняется | Что добавляется к базовому контролю |
| --- | --- |
| Локальная геометрия, скругление, интервал | Реальный hover/focus/selected, если они затронуты; сравнение вложенных контуров и соседних осей. Не повторять аудит всего сайта. |
| Сетка, типографика, длина текста | 320 CSS px, промежуточные брейкпоинты, короткое окно, увеличение текста до 200%, порядок чтения и отсутствие обрезания. |
| Общий материал, цвет, тема | Затронутые семейства компонентов; контраст на реальных светлых, тёмных и пёстрых подложках; погодные варианты, уменьшенная прозрачность и запасной материал. |
| Раскрытие, меню, якорь | Мышь, клавиатура, touch; вход и выход; Escape, Back, фокус, прямой фрагмент URL, изменение ширины при открытом меню; HTML без JavaScript. |
| Видео | Один запуск по намерению, пауза, повтор, переход ко второму ролику, нативные controls, субтитры и ошибка загрузки. Проверка изменённого мобильного сценария обязательна. |
| Анимация или hover-превью | Прерывание и повтор, отсутствие скачущих целей, touch/keyboard-альтернатива и reduced motion. |
| Сетевая логика или сохранение настроек | Ожидание, отказ сети/хранилища, устаревшие данные, повтор и доступность основного содержания при сбое. |
| Только документация | Точность ссылок, согласованность правил, область применения и diff. Повторный визуальный аудит неизменённого интерфейса не нужен. |

Браузерный viewport не доказывает поведение физического телефона. Автоматический WebKit не называется реальным Safari. DOM-проверка и дерево доступности не заменяют скринридер. В отчёте указывать фактическую среду.

## Сценарии для проверки затронутого пути

Выбирать применимые сценарии; не выдавать этот список за протокол уже проведённого пользовательского исследования.

| Путь | Ожидаемый результат |
| --- | --- |
| Выбор помощи | По видимым услугам можно различить формат, стоимость и назначение. Подробности доступны без вложенного аккордеона; открытые сопоставимые варианты не мешают сравнению. |
| Проверка тренера | Из биографии и результата понятны автор, контекст и подтверждённые факты. Краткий тизер приводит к полной истории, не повторяя её целиком. Оригинальный отзыв читается и на узком экране. |
| Просмотр видео | На телефоне одно нажатие строки запускает соответствующий ролик. Доступны пауза, звук, повтор и субтитры. Второе видео останавливает первое; основные факты можно прочесть. |
| Навигация и раскрытия | Переход ведёт к видимому содержанию; закрытая целевая история открывается. Меню закрывается, фокус и прокрутка восстанавливаются. После Escape, Back и смены ширины нет блокирующего слоя. |
| Выбор темы | Система, светлая и тёмная темы различимы, выбор сохраняется при разрешённом хранилище, применяется на 404. Нельзя принять hover за текущее значение; погода не отменяет ручной выбор. |
| Клавиатура и увеличение | Действия достижимы в логичном порядке, фокус виден; подписи и цены не обрезаны при увеличении текста. На ширине 320 px сама страница не уезжает по горизонтали. |
| Связь | Назначение ссылки соответствует подписи, личный контакт отличается от канала. Текст объясняет, что можно написать. Для проверки не отправлять сообщение реальному человеку. |
| Сбой дополнения | Недоступные погода, видео или хранилище не лишают человека услуг и контактов; нет ложного успешного состояния или выдуманных данных. |

## Перед публикацией

Выполнить обязательные проверки из `AGENTS.md` один раз для итогового состояния:

```sh
python3 scripts/check_static.py
node --check script.js
node --check theme.js
node --test scripts/theme.test.cjs
git diff --check
```

При изменении других скриптов проверить их синтаксис и запустить относящиеся к ним существующие тесты. Полный набор команд репозитория приведён в `README.md`; требования CI остаются действующими. Не создавать тесты, которые лишь повторяют декларацию CSS или проверяют существование этого чеклиста.

- [ ] Просмотреть итоговый diff: он отвечает запросу и не меняет посторонние факты, изображения или одобренную композицию.
- [ ] Проверить затронутый рендер и взаимодействие по выбранным выше сценариям. Новый или усугублённый дефект исправить до сдачи.
- [ ] После публикации проверить точный SHA, результаты Static checks и GitHub Pages, затем публичную версию с учётом кеша. Для визуального изменения открыть опубликованный изменённый экран.
- [ ] Прежние дефекты вне задачи и непроверенные среды назвать отдельно. Нельзя написать «всё проверено», если проверена только одна тема или имитация устройства.

При изменении только документации проверяется опубликованная редакция документов; повторять визуальную приёмку неизменённого сайта не требуется. Это не исключение для сопутствующего изменения HTML, CSS или JavaScript.

## Краткая запись результата

Достаточно записи в ответе или релевантном журнале проекта. Не нужен отдельный отчёт на каждую микроправку.

```text
Изменение / SHA:
Сценарий и затронутые правила:
Среда, ширины, темы и состояния:
Что выполнено автоматически:
Что просмотрено и пройдено в браузере:
Результат / ссылка на снимок при визуальной правке:
Публикация / публичная проверка:
Ограничения и отдельные прежние дефекты:
```

## Когда проверяем гипотезу с посетителями

Для существенного изменения предложения, иерархии услуг или раздела результатов сформулировать исследовательский вопрос и план по N36–N37. Это отдельная проверка, а не основание задерживать уже согласованную точечную правку до набора участников.

Примеры нейтральных заданий: «Вы хотите подготовиться к первому заплыву; выясните, какая помощь вам подходит и сколько она стоит»; «У вас есть тренировки, но непонятно, что мешает прогрессу; найдите подходящий формат»; «Решите, достаточно ли вам сведений о тренере, чтобы обратиться, и объясните решение».

Наблюдать маршрут, ошибки, возвраты, непонятые условия и достижение цели. Участник не обязан реально писать Кате. Вопрос «нравится ли» не заменяет наблюдение. Около пяти подходящих участников одной однородной группы — ориентир первого качественного раунда, не статистическая оценка доверия или конверсии и не гарантия обнаружения всех проблем.
